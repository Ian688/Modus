# Modus × 12 项目对比详细附录

> 数据来源：2 轮 14-agent 工作流原始输出（对比综合 10 维度 + 盲区扫描 4 视角）。主文档见 learning-synthesis.md。

## 一、10 维度对比全量缺口

### Agent 循环与策略

**跨项目共性模式**：确定性循环健康守护是 4 项目共识：loop-context 熔断器（errorSignature+trigram）、peri speculation_guard（speculation 词命中+连续工具轮数≥6）、CCB 3-strike blocked（同因连续 3 次才判死）、GenericAgent plan 完成声明拦截（需 [VERIFY] 证据）——共同结论是'卡死/跑飞/深挖检测必须零 LLM、纯信号、可单测，与模型判断解耦'，且触发后不是硬断而是注入上下文/升级到人；'目标驱动续跑'三件套被独立实现 3 次：状态机（CCB 7 态/peri GoalController）+ idle 钩子注入 steering 元消息（CCB useGoalContinuation 注入 <goal-steering>/peri 3 级递增紧迫感/GenericAgent goal_mode 唤醒注入）+ 模型侧回执工具（GoalTool complete/blocked，CCB/peri 都有）——这是'进攻性驱动'的标准解法，Modus 只有防御性的一半；循环从单 while 演进为'阶段化 + 消息队列消费 + idle 等待'：peri RCRA 四阶段（Receive 唯一消费/退出判断点）、pi steer+followUp 双队列、CCB 命令队列+idle 钩子、supervisor tick 全局节拍+事件监听器——共识是把用户输入、后台事件、goal 续跑统一成队列+消费点，单 while 循环无法优雅吞并异步事件；上下文密度是成本工程而非功能：peri（prompt cache 静态/动态边界+3 断点+三层 compact re-inject 最近文件）、pi（会话树+结构化压缩切点不切 toolResult+文件操作清单）、GenericAgent（<summary> 物理快照折叠+工具库去重注入+网页 DOM 密度化）都在'控 token 而非堆信息'，与 Modus 单层 compressor 的差距是全维度的；把'结束/停止'变成可编程事件而非会话终点：claude-code Stop hook 阻断退出回灌（ralph-wiggum）、CCB budget_limited 注入总结 prompt 而非硬断、peri block_continue 强制续跑、GenericAgent [VERIFY] 才放行完成声明——共识是退出语义应由循环持有并可被策略改写；策略从'提示词'升级为'可机械执行+可跨进程'的契约：loop-gate exit-code(0放行/1告警/2升级)、CCB Pipe 权限桥（跨进程审批转发）、cc-haha deny 作为 tool_result 回灌模型（不 abort，让模型'看到拒绝'）——偏安全维度但直接改变循环内策略决策的形态

**已超车（不重复建设）**：三策略 reasoner 架构：react/plan_execute/select（确定性启发式：多步线索+文件意图→PlanExecute）——12 项目里没有等价物，CCB/loop/peri/pi 全是单一循环，无策略分派层；run budget 周期持久化 + interrupt 恢复：防御性'防跑飞'已是多数项目缺失的能力（loop 靠日预算 JSON、CCB 靠 cost-tracker、pi 无持久化），Modus 已有落盘+恢复闭环；中途确定性压缩（保护头尾+尾部引用，无 LLM）：比 pi 的 LLM 结构化摘要、GenericAgent 的纯文本协议折叠更省且不打断循环，且被 approve-then-execute 不变量约束；provider 瞬时重试 approve-then-execute：只在零产出时重试、内容已流出绝不重放——pi 的 retry.ts 和 GenericAgent 的 MixinSession 都没有这条不变量；子任务递归 + 后台任务模型（进程注册表落盘 + reaper + atexit/SIGTERM 清理）：supervisor 的进程状态机是缺口但整体后台任务生命周期模型 Modus 已领先（cc-haha 反例证明 bypassPermissions 定时任务是坑，Modus 不会踩）；六条安全不变量 + 高解耦高插拔架构：循环层的安全集成（ApprovalPolicy/CommandGuard/PathGuard 进循环）是 Peri（YOLO 默认开）/Pi（无权限系统）/GenericAgent（信任 LLM 自律）有意留白而 Modus 已填的能力；已自研 MCP client/server、skills（SkillRepository）、moa、peri consensus、worktree 生命周期——loop 的 mcp-server 知识资源、CCB 的 worktree 隔离 Modus 已有底座，只需增量；Desktop WS server + kanban（board_aggregation 纯函数聚合）+ annotate.js 批注回传：Agent 循环的产物可视化层已超过 beads/cc-haha 的'只读投影'（beads 看板实测拖拽未接线、只读）；作用域化/静态 JSON 确定性评分与轨迹落盘：AssetOpsBench 的轨迹→离线重评分闭环属评估维度（I），但 Modus 的 run 状态落盘已是其前置设施，评估器接入成本低

### 安全/审批 HITL

**跨项目共性模式**：HITL 从『二元门禁』演进为『可回灌回路』：拒绝不是 abort 而是结构化 tool_result 让 agent 看见理由并调整（cc-haha deny→tool_result + hermes /deny 带理由 + peri 4 决策含 Edit/Respond），确认结论同样是 schema 强制的结构化工具而非文本承诺（PentesterFlow confirm_finding 强制 payload/response_excerpt/curl）——『Confirmed means reproduced』与『拒绝要可见』是同一哲学的两面；审批缓存/放行必须绑定载荷而非工具粒度：PentesterFlow（cacheKey 绑改写后命令/origin/路径）+ peri（(tool_name, input_hash) 5min 缓存）+ hermes（session 级 yolo）——三家用同一条防线：防止一次允许=一类全放；降人工在场成本是 HITL 共性工程方向：guardian/classifier LLM 三态分流只把不确定的给人（hermes _smart_approve + peri LlmAutoClassifier），审批请求则转发到控制者侧统一决策——CCB pipe 权限桥（slave→master 审批 UI）、peri broker/multiplex 竞速（TUI/IM/Channel）、cc-haha GUI 排队批量审批。Modus Desktop WS 天然是现成『控制面』；无人值守/后台场景必须 fail-closed 且继承审批策略、绝不 bypass：hermes（无人在场自动 deny、subagent 默认 auto-deny）、loop（agent 不可自提预算 cap 须人改）+ cc-haha cron 强制 bypassPermissions 是被点名的反例——Modus 若做定时任务应默认继承而非静默全放行；审查粒度从『每工具调用』上移到『变更事件/变更集』级：claude-code（git baseline diff + commit/push 事件闸 + SHA 去重 + 限流）、loop（gate.yaml + exit 2 升级到人）——成本更低、覆盖面更全，且天然接进 CI/脚本契约

**已超车（不重复建设）**：deny-first Capability enum 门 + Permission ladder T0-T5（LOCKED→LENS→SCOPED WRITE→EXEC→DESTRUCTIVE→IRREVERSIBLE）：GenericAgent（无沙箱/无阶梯/ask_user 自愿可绕过）、Pi（显式『无权限系统』、README No permission popups）、Peri（YOLO 默认开、无权限阶梯）、beads（CORS Any + 0.0.0.0 无认证）全部远弱于 Modus，不需学；CommandGuard 复合命令/解释器逃逸拦截 + PathGuard 工作区路径锚定：Peri 的 Bash 是 bash -c 原样拼接无拦截、Pi 无 PathGuard（路径不锚定工作区）、CCB workflow 沙箱只保确定性不保安全（注释自认）、beads 的 worktree 命令参数不查 home 内；CLI 终端审批 HITL 已成型（rich 卡片 + y/N + ask_complete_async 透传 approval_callback）：对比 GenericAgent 的 ask_user 靠模型自律、Pi 明确不做审批弹窗；AuditLog + 六条安全不变量测试：Peri 无 AuditLog（安全事故无法取证）、Pi 的安全是『文档声明』而非测试门、beads 无审计；approve-then-execute 不变量（内容已流出绝不重放）：provider 瞬时重试只在零产出时重试，与 hermes 『命令文本视为不可信输入』同理，Modus 已内建；MCP server 默认只读 lens + 同源 /api/preview 代理 + 进程级清理（atexit/SIGTERM + reaper + 进程组 kill）：beads 的 0.0.0.0 监听 + CORS Any + 无 CSRF 是本类产品典型安全债，Modus 同源代理设计有相对优势；拒绝熔断前的底牌——HARDLINE 无条件封杀式能力已由 Capability deny-first 门 + Permission ladder 的 IRREVERSIBLE 级承担，guardian LLM 只是加分项而非必需品

### 进程/任务生命周期

**跨项目共性模式**：长生命周期任务都抽象为'显式状态机 + 落盘 + 恢复语义'：supervisor(8 进程态)、hermes(suspended/resume_pending/active + clean_shutdown)、CCB(goal 7 态 + JSONL hydrate)、pi(会话树 + 断点续跑)——Modus 只有 run budget 快照，任务是'无态'的，这是该维度最大的结构差；'卡住'从终止信号升级为可注入的管理信号：loop(stagnation/frustration→exit 2 升级到人)、CCB(budget_limited 注入总结 prompt 而非硬断 + blocked 3-strike)、peri(speculation_guard L1/L2 分级提问)、GenericAgent(goal_mode 禁止提前宣布完成)——共同洞察：无进展不是硬停，而是注入'已试过什么/失败模式/下一步'可读管理块；后台/子进程→主循环从'轮询结果'改为'订阅事件+唤醒续跑'：supervisor(EventListenerProtocol 令牌协议 + Tick 全局节拍)、peri(idle suspended + inbox.await_wake)、hermes(has_active_processes 阻止过期)、CCB(Pipe 跨进程审批转发)——Modus 的 spawn/tail 是拉模型，改事件推送是 P1 共性方向；任务关键节点应事件化+门控化+可审计：claude-code(commit/push 事件化审查 + reviewed-shas SHA 去重)、beads(worktree-per-task 合并门 + 合后自动关任务/清 worktree/rebase 兄弟)、CCB(GoalTool complete 带 usage 审计)——'提交/合并/完成'这些生命周期转折点是审计与门禁的最佳挂点，Modus 目前只有单点工具验证

**已超车（不重复建设）**：后台任务模型底座齐全：spawn/list/tail/kill + 进程注册表落盘（~/.modus/processes/meta.json，断电后孤儿可检）+ 后台 reaper + atexit/SIGTERM 双通道清理（2s grace SIGTERM→SIGKILL，幂等）+ 进程组隔离——对比项里 PentesterFlow 无后台任务模型、supervisor 无审计、pi 靠信任+容器，Modus 已超车，不重复建设；run budget 周期持久化 + interrupt 恢复 + stalled_for 雏形：budget.py 的 TurnRecord.made_progress + stalled_for 已是 token/text 级停滞信号（含 warmup 防误判），loop-context 的停滞检测只需在其上升级信号，不是从零建；进程组 kill（负 PID）+ 有界 tail（64KB）+ 注册表 50 行上限 + 有界扫描截断披露：大结果控制与进程清理已到位，与 pi shell.ts killProcessTree/trackDetachedChildPid 同源且 Modus 已有；进程/任务审批与审计面全面领先：deny-first Capability 门 + T0-T5 权限阶梯 + AuditLog + 六条不变量 + 后台 spawn 走能力门——supervisor 认证后全权无审计、CCB Pipe 裸 TCP 无认证（自列 P0 待办）、hermes 审批门自认'启发式非边界'、pi 无权限系统，这些项目的进程安全模型一律不吸收；避开反模式：AssetOpsBench 的 plan-execute 每工具调用起一个新 MCP stdio 子进程是性能反模式（报告标注），Modus 工具执行统一走 executor + 进程注册表，不学'每调用一个子进程'；subtask 递归有界（max_depth 递减）+ 共享预算/审批/工作区，比 GenericAgent 的 subagent 文件协议（input/output/reply/_stop 六文件，无权限边界）更安全

## 二、盲区扫描全量方向

### 生态视角

**总判断**：从互联生态视角，Modus 最大的盲区不是缺协议、缺工具，而是它的安全机器是单进程私有的——T0-T5 阶梯、ApprovalPolicy、能力门这些独特资产在跨进程那一刻全部退化成二值开关，同时工具命名用哈希把能力身份抹掉，插件面是纯占位。生态成熟后决定成败的不是"能连多少 MCP"，而是三件事：信任可携带（把策略序列化上 wire）、能力可发现（把哈希换回语义身份）、扩展可信任（签名+能力映射+撤销）。而本地/云分工则是让 Modus 从"单机全能"升维成"个人 agent 网格枢纽"的唯一路径——这四个方向都复用 Modus 现有模块做边界层，不做新内核。

#### 跨进程信任序列化：把 T0-T5 权限阶梯搬到 MCP 线上（Agent 身份与可验证信任）

- **thesis**：Modus 内部的安全资产是世界级的——capability deny-first 门、ApprovalPolicy、T0-T5 阶梯、AuditLog——但这一切在跨进程那一刻全部坍塌成两个二值：`read-only lens` 或 `requires_approval=True`。mcp_client.py 对每个远端 MCP 工具无条件 `requires_approval=True`，mcp_server.py 只透传 name/description/inputSchema。生态成熟的标志不是'能连'，而是'信任可以携带、验证、撤销'。真正没人想到的是：策略本身（capability class + 读写性 + 是否需要审批）应当被序列化，作为工具的一部分随线传输，让远端接收方不用重新猜，让本地不用全问。
- **whyBlind**：安全团队都在做单进程内部威胁，协议团队都在做 JSON-RPC 帧格式——双方都不会想到把'策略'本身编码进线上元数据。而且哈希命名让工程上'名字稳定'很好看，恰好掩盖了'能力与信任信息被一并抹掉'这个生态灾难
- **Modus 触点**：tools/base.py(Tool 声明)、tools/capabilities.py(capabilities_granted)、policy/approval.py(ApprovalPolicy)、policy/audit_log.py(provenance)、mcp_client.py(McpServerConfig)、mcp_server.py(_tool_schema 过滤逻辑)、redact.py(脱敏习惯)
- **风险**：签名验证误配会锁死合法工具（保守回退到 ASK 保安全但体验退化）；ed25519/trust store 是全新的密码学面，审计负担上升；协议尚无非官方标准，可能成为单方面扩展；与现有对无条件 ASK 的调用方存在兼容迁移成本
- **payoff**：把 Modus 独有的安全机器变成协议层独占优势——远端工具'开箱即带策略'，本地 HITL 从'全问'收敛到'只问真正危险的'；外部 agent 接入 Modus server 时复用同一信任模型，安全不随进程边界流失。生态成熟后这是护城河而非功能
- **落地步骤**：在 `tools/base.py` 的 Tool 增加 provenance/trust 向量：`source_kind`(builtin/local_plugin/remote_mcp)、`origin_identity`、`policy_capsule`（capability class + 读写性 + 需不需要审批的 JSON 块），由 `mcp_client.py` 的 McpServerConfig 携带并落 AuditLog 的 provenance 字段；新增 `attestation.py`：ed25519 签名 + 本地 trust store `~/.modus/trust.json`（reuse `redact.py` 的脱敏习惯）。远端 MCP server 若在 `tools/list` 里提供带签名的能力胶囊，客户端按 tier 自动放行；否则回退到今天的无条件 ASK（fail-closed，不回归）；把 T0-T5 阶梯映射到远程调用：T1 lens 自动放行、T2 需 capability match + 审批、T4/T5 远程一律拒绝——reuse `tools/capabilities.py` 的 `capabilities_granted` + `policy/approval.py`，不新建另一套策略，只做序列化；mcp_server.py 的 `_tool_schema` 增加 `capabilities` 与 `policy` 字段（非只读时带上可验证签名），让 Modus 自己的 server 成为'信任元数据参考实现'，外部 agent 直接复用

#### 能力清单（Capability Manifest）与发现协议：把哈希命名换回可搜索的能力身份

- **thesis**：Modus 目前所有工具互操作都建立在'一个平铺的字符串列表'上：tools/list 返回扁平名字，名字还被故意哈希成 `mcp__{server_digest}__{tool_digest}` 来防冲突。这等于把能力身份一起抹了——无法按语义查'哪个 server 提供 filesystem.read'、无法跨 agent 去重、无法做能力路由。生态成熟后，个人 PC 基座需要一个'搜索自己工具生态'的原语，就像包管理器之于库：不是遍历字符串，而是按能力 URI 查询。
- **whyBlind**：哈希命名从'工程正确'角度无比正确（名字稳定、零冲突），所以没人质疑它；但正是这种'工程上漂亮'掩盖了'生态上不可查询'。每个人都把 tools/list 当 API 调用而不是身份系统，能力发现被认为是'协议层的事'而不是'应用层的事'，于是永远没人做
- **Modus 触点**：mcp_server.py(tools/list + initialize)、extensions.py(_mcp_tool_name 哈希命名)、tools/code_index.py(per-root SQLite 索引模式)、desktop/db.py、mcp_client.py(list_tools/选择逻辑)、tools/registry.py
- **风险**：能力 URI 命名空间尚无生态共识，过早固定可能被后续标准推翻；语义命名在跨 provider 时存在歧义（'read' 在不同源里语义不同），需强 schema；改命名涉及 MCP 工具名兼容迁移
- **payoff**：让'我有哪些能力'成为可查询的结构化资产：跨 agent 去重、按语义路由、插件生态可搜索。Modus 作为参考实现占据定义权，外部 agent 以 Modus 的 manifest 为事实标准——生态成熟后这等于拿到协议层的话语权
- **落地步骤**：定义 `ModusCapabilityManifest`（JSON Schema：capability URI 如 `modus://cap/filesystem.read` + policy caps + manifest 版本），在 mcp_server.py 的 `initialize` 响应与 `tools/list` 里发出；对外成为参考实现，对外部 agent 是'照抄我'的模板；新建 `tools/discovery.py`：把本地插件 + 已连接 MCP server 的能力清单索引进 SQLite（reuse `tools/code_index.py` 的 per-root 索引模式 + `desktop/db.py`），提供 `find_capability(class, query)` 查询'哪个源提供什么能力'；改 `extensions.py` 的 `_mcp_tool_name`：从 digest 命名改为 'capability slug + source 限定路由表'——碰撞安全从名字移到路由层，能力身份恢复为语义，名字可读、可查、可审计；在 mcp_server.py 增加 `capabilities/list` 方法（能力粒度，超越 tools/list 的字符串粒度），mcp_client.py 优先用能力清单做选择而非逐个试调用

#### 可信插件市场前置：签名 + 能力映射 + 撤销，而非'能装 MCP 就是有生态'

- **thesis**：extensions.py 声明了 skill/mcp/plugin 三种 kind，但 plugin 是纯占位符，skills 只是裸 JSON {name, description, prompt}，唯一真实扩展通道是 MCP 的 stdio——它在你的机器上 spawn 任意子进程、还能联网。这恰好是 rootkit 的安装面：生态成熟时'装插件'的默认前提不是加载器而是防投毒。Modus 已经有完整执行面（executor deny-first + ApprovalPolicy + capabilities_granted），差的只是边界那几块，做出来就是护城河。
- **whyBlind**：插件市场被想象成'商店 + 下载'，没人愿意做安全又无聊的安装层；而且 Modus 自己有 mcp_server 的教训（第一版 call_tool 绕过 ApprovalPolicy 真的写了文件）——教训在记忆里，却没有物化成'任何扩展面都强制走门'的边界机制。团队忙着加能力面，没有给能力面加'身份'
- **Modus 触点**：extensions.py(plugin 占位 + contribute_tools)、skills.py(Skill 数据结构)、mcp_server.py 的安全教训（call_tool 曾绕过 ApprovalPolicy）、tools/executor.py(deny-first)、tools/capabilities.py、entrypoints/cli.py、desktop/db.py
- **风险**：签名基础设施（密钥分发、撤销传播）对个人 PC 用户是理解门槛，可能劝退小白；过度加固会让插件生态启动慢于宽松竞品；ed25519 依赖与离线场景冲突，纯离线用户无法验证新插件
- **payoff**：生态成熟时'装插件'的默认前提不是加载器而是防投毒——签名验证 + 能力声明映射进 deny-first 门 + 版本固定 + 撤销清单。所有竞品都在做'能装更多插件'，Modus 做了'装了不被搞'，这是唯一可持续的差异化，且复用现有执行面，边际成本低
- **落地步骤**：在 `skills.py` 的 Skill 与 `extensions.py` 的 ExtensionDefinition 增加 version/author/signature(ed25519)/min_capabilities 字段；SkillRepository 保存前校验 name 之外还要校验签名与能力声明；实现 extensions.py 的 plugin 加载器：读 manifest → 验签名（新 `attestation.py`）→ 能力映射进 `capabilities_granted` 门 → 工具 handler 注册进 executor，走 deny-first + ApprovalPolicy（沿 mcp_server 安全教训：任何执行面都不许绕过门）；新增 `modus registry add|remove|list` CLI 子命令（entrypoints/cli.py）+ 本地注册表索引（reuse db.py）；签名校验失败或能力越界默认拒绝，revocation list 落盘 `~/.modus/trust.json`；McpManager（mcp_client.py）连接前校验服务器指纹与签名，拒绝已撤销/未签名的 server；skills 目录加入 `dist-info` 式的版本与来源元数据，为更新/回滚留位

#### 本地/云分工的委托协议：PC 作主权枢纽，云端作临时雇工（agent_delegate）

- **thesis**：Modus 已经具备本地/云分工的全部零件：model_repository 的路由、moa 的多模型角色、process_tools 的本地进程、run ledger + budget 快照的可恢复性——但没有一层策略说'这个任务留在本地、那个派给云端 agent，且委托可审计、有界、可续跑'。生态成熟后个人 PC 基座的位置不是'单机全能'而是'agent 网格的枢纽'。`spawn_subtask` 就是本地版的形状——把子目录隔离换成远端端点，就有了委托协议。
- **whyBlind**：团队在单进程 REPL 里打磨'全能'，把本地/云分工当成性能优化而不是架构选择；而且它需要同时会 trust（方向1）、路由（model_repository）、可恢复（run ledger）三块才能启动，单点做都是半吊子，所以没人碰。另一个原因是'云 agent'在 2026 仍各家自封闭，反而让'谁先做中立委托协议谁先成枢纽'的窗口更大
- **Modus 触点**：desktop/model_repository.py(路由/凭据)、agent/moa.py(多模型角色)、agent/subtask.py(委托形状 + max_depth + 子目录隔离)、desktop/orchestration_ledger.py + policy/audit_log.py(委托记录)、desktop/db.py(interrupt_nonterminal_runs + budget 快照)、tools/process_tools.py(本地进程对照)
- **风险**：远端 agent 无法验证行为（不透明委托），需强授权 + 审计才能兜底；需要 trust/路由/可恢复三块同时成熟才能启动，单点做都是半吊子，投入大；当前无中立远端协议生态，早期只能对接自家或少数 agent，落地慢
- **payoff**：让 Modus 从'单机全能'升维成'个人 agent 网格的枢纽'：本地持有记忆/策略/状态，把自包含子任务外发给远端 agent（携带能力授权 + 预算上限 + 限域凭证），收回有界结果。模型无关性在此真正落地——边界上发的是任务 + 授权 + 预算，不是 OpenAI 兼容 API 调用
- **落地步骤**：定义 `RemoteAgentProfile` dataclass（base_url + 模型无关的任务端点 + capability 授权集 + budget 上限 + 限域 scope token + 期望 attestation），存进 model_repository 同款 JSON 配置，reuse `desktop/model_repository.py` 的 `_normalize`/`_store_credential` 模式；新增 `agent_delegate` 工具：任务形状复用 `agent/subtask.py`（自包含 + max_depth + 子目录隔离），把子任务发到远端端点，返回有界结果 + 预算快照；委托记录进 `desktop/orchestration_ledger.py` + AuditLog（带 provenance）；路由策略 local-first，四维决策：数据体量、所需能力是否本地有、密钥/数据邻近性（含敏感性的就近优先）、成本——reuse model_repository 的 runtime_models + moa 角色配置作为打分输入；委托恢复：复用 `desktop/db.py` 的 `interrupt_nonterminal_runs` + budget 快照，远端结果不可达时标记 interrupted 并支持重试，跑通'断电/断网后续传'闭环（呼应 modus-power-loss-guard 记忆里的 checkpoint-resume 缺口）


### 架构视角

**总判断**：从架构演进视角，Modus 最深层的工程盲区不在『缺什么能力』，而在『持久化的最后一公里没走完』与『单机单进程的隐含假设』。四个方向按杠杆排序：(1) 事件溯源的 Run 状态机——agent 循环本身不可重放，崩溃=重付一次，这是和一次性脚本的分水岭；(2) 进程出身身份——orphaned 被写进 schema 当终态，且裸 pid+killpg 存在 PID 复用误杀隐患；(3) 机器无关身份——code_index/workspace 全用绝对路径哈希作 key，『任意 OS/换机器』的数据迁移地基是空的；(4) 多实例协调与 schema 版本化——CLI/Desktop/MCP 裸写同一个 desktop.db，无锁无版本号，升级与并发都是概率性事故。这四者共同指向：Modus 的『能力密度』已远超其『结构韧性』，先补韧性，能力才可信。跨 OS 的深层一致性不是独立方向，而是这四个方向的公共底层——进程语义、崩溃恢复、数据迁移、并发协调在 macOS/Linux/Windows 上各自分裂，收敛它们的抽象应该在每个方向内一并解决，而非单独建一层。

#### 事件溯源的 Run 状态机：让 agent 循环本身可重放（而非只把 side-effect 落盘）

- **thesis**：Modus 的持久化哲学是『一切关于 run 的都落盘，但 run 本身不落盘』——db.py 有 13 张 run 事件表、budget 有 snapshot()、session_state 有 park_run，但 agent.py 的循环决策状态（history、controller、pending_approvals、subtask 栈）全部是 RAM 里的对象。杀掉进程，transcript 完好，循环却死了。桌面端把 run 标记为 interrupted 然后让用户重开，等于把已发生的钱重付一次，而且跨 OS 语义（Windows 无 SIGKILL 组、无 killpg）让重启恢复在不同平台上行为都不一致。真正的基座应该让 run 是可重放的纯函数：事件写进 DB，重启后从最后一个 durable 状态续跑。
- **whyBlind**：因为『落盘』已经被大面积完成了，容易产生『run 已经持久化』的错觉——budget 快照、run_events、approvals 都在写盘。但没有任何代码能从这些事件重新构造一个活的循环。开发者和评审都会被『事件表已存在』骗过去，没人检查『能不能 replay』这个更硬的命题。
- **Modus 触点**：src/modus/desktop/db.py run_events 表 · src/modus/runtime/budget.py snapshot() · src/modus/agent/agent.py 与 strategies/plan_execute.py 的循环 · src/modus/desktop/session_state.py park_run/active_run_id
- **风险**：工具调用不可重放（非确定性外部副作用）；事件体积与 LLM 重推成本；reducer 化会动到 react/plan_execute/select 三个策略的共享骨架，回归面大。
- **payoff**：长周期 run 第一次具备真正的断电/崩溃韧性——不是『标记中断让你重开』，而是『从断点继续』。这是『个人 PC 基座』和『一次性脚本』的分水岭：让用户敢把需要跑一小时的任务挂上去。
- **落地步骤**：把 agent 循环重构成纯 reducer：run(state, LLM response) -> (state', events)，events 直接追加进 db.py 已有的 run_events(modus.agent-event.v2)；history 不再作为唯一的真相，而是事件的派生视图。；给 runtime/budget.py 补 from_snapshot() 作为 snapshot() 的镜像，并把 snapshot 从『budget 计数器快照』升级为『循环状态快照』（含 controller 的 pending tool 状态）。；新增 resume 路径：启动时读 DB 找最近一条 interrupted/process_restart 的 run，在**新进程**里重建循环、从断点事件继续，而不是只改状态标签。；加一个 replay 测试：杀掉模拟的 run 进程，断言新进程能在相同 DB 状态上续跑并产出与连续运行等价的工具调用序列（非确定性工具用 mock）。

#### 用『进程出身』替代 pid 作身份：终结 orphaned 弃儿 + 堵住 PID 复用误杀

- **thesis**：当前进程模型把『orphaned』写成了 schema 里的合法终态——文档明说 daemon 所有权/reaping out of scope。这是自欺：一个基座声称能 spawn 后台进程，却在自己崩溃后把进程遗弃给用户『自己决定』。更糟的是 kill_process 用裸 pid + killpg(SIGKILL)，没有任何出生时间校验：Modus 崩溃后 registry 里的 pid 被 OS 回收给另一个无辜进程，用户一调 kill_process 就 SIGKILL 掉别人。跨 OS 这层更分裂——macOS/Linux 用 start_new_session+killpg，Windows 用 taskkill /T，无统一的 ownership 抽象。
- **whyBlind**：因为『orphan 检测』看起来像是一个被做掉了的功能（状态机里有个 orphaned 状态，还有 _owned_by_this_process），所以没人再往深挖。但『检测并上报』和『接管并恢复』是两个量级的承诺。PID 复用误杀是隐藏 bug——registry 有 50 行的保留窗口，崩溃后重开，误杀的概率真实存在。
- **Modus 触点**：src/modus/tools/process_tools.py spawn/kill/_pid_alive/_owned_by_this_process · src/modus/process_cleanup.py atexit/信号清理 · src/modus/policy/command_guard.py（spawn 已过 CommandGuard）
- **风险**：os 各异的 start-time 解析（Windows 无 /proc）；误接管会杀死用户想保留的进程，需要明确语义；改动会碰既有 HITL 审批链。
- **payoff**：直接补上 function-map 里标注的『最大缺口=后台进程工具集』的最后一环：让长生命周期进程（下载、训练、批处理）成为可被信任、可被救回的一等公民。杀掉 PID 复用误杀这个潜在数据破坏 bug。
- **落地步骤**：spawn 时额外记录 born_at（/proc/<pid>/stat 或 ps -o lstart），kill/tail 前先校验 pid 的启动时间与 meta 一致，不一致即判定 PID 复用并拒绝操作。；新增接管路径：重启时发现 orphaned 且 alive 的 registry 条目，提供 `modus adopt <id>`（或 Desktop 一键）把所有权从旧 pid 转移到当前实例，而不是只报告。；kill_process 增加 ownership + approval：非本人 spawn 的进程、或 orphan 接管前，一律 requires_approval=True；同时把 atexit 清理改为默认不杀（除非 daemon 模式），避免正常退出误杀用户想留着的后台任务。；为 macOS/Linux/Windows 三个后端建立统一的 ProcessOwner 抽象（出身校验、组信号、孤儿判定），收敛现在散在各处的 sys.platform 分支。；补回归测试：mock 一个被回收的 pid + 真实 start time 不匹配，断言 kill_process 拒绝而非 SIGKILL。

#### 机器无关的身份与数据迁移层：把『绝对路径哈希』换成可移植的稳定身份

- **thesis**：整个 identity 体系钉死在机器上：code_index 用 sha1(resolved root) 做 key，workspace digest 用 resolved root，db 行存绝对路径，进程日志/audit 都在 ~/.modus。这意味着『换机器』或『macOS→Linux』之后，索引全部失效、workspace 身份全部漂移、迁移只能靠手动拷贝整个 home。对一个宣称『任意 OS/平台可用、个人 PC 基座』的产品，这是最大的自我矛盾：数据是它最大的资产，却连一份 `modus export` 都没有。看不见，是因为你从不换机器——但这恰恰是基座的差异化能力。
- **whyBlind**：身份键现在『恰好能用』（单机单用户场景无感），代码注释还写着『per-root 隔离，never collide』——把本地正确性当成了完整性。没有一套独立于 OS 路径的稳定 id，所有『迁移/备份/多机同步』的后续工作都会被地基卡死，而现在没人会为此立项，因为没有 bug 报出来。
- **Modus 触点**：src/modus/paths.py data_dir/data_path · src/modus/tools/code_index.py _root_key 哈希键 · src/modus/desktop/workspace.py WorkspaceIdentity · src/modus/desktop/db.py 绝对路径行 · src/modus/desktop/credential_backend.py 凭据后端
- **风险**：迁移期间旧索引失效需要触发重建的路径；UUID 落地会破坏既有单机工作流的既有 hash 键，需要兼容窗口；多机并发写同一数据目录仍无解。
- **payoff**：『任意 OS/任何机器，同一基座』第一次成为字面成立的承诺，而不是口号。数据可迁移是个人基座信任的地基，此层一动，备份、多机同步、换机 onboarding 全部解锁。
- **落地步骤**：给 WorkspaceIdentity 引入稳定的 workspace_id（UUID，首次打开写入 .modus/workspace.json 或数据目录），code_index 改用 id 做 key，路径只作 display。；db.py 的 workspaces/runs 行改为存 workspace_id + 相对锚点，打开时按数据目录解析绝对路径，迁移后的机器自动重建索引（rebuild on miss）。；新增 `modus export/import`：sqlite dump（含 schema 演进）+ 通过 credential_backend 的导出（keychain 存 marker、JSON 存密文）+ 触发 code_index 重建，产出单一归档。；写一份 portability 契约文档：哪些数据可移植、哪些绑定机器（keychain、系统服务、已 spawn 进程）、升级时的迁移顺序。；加跨目录移动的回归测试：把数据目录 mv 到新路径/新前缀，断言 workspace 身份不漂移、索引可重建。

#### 多实例协调 + schema 版本化：同一个 desktop.db 的并发写者现在是裸奔的

- **thesis**：CLI、Desktop server、MCP server、spawn 的子进程共享同一个 desktop.db 和 ~/.modus，但全仓库没有一个 flock/lockfile、没有 PRAGMA user_version，schema 演进靠 db.py 里散落的 _ensure_column ALTER。这意味着：用户同时开 CLI 和 Desktop、或两个 Desktop 实例，就是两个 writer 裸写同一个 SQLite——lost update 和 WAL 锁冲突是概率问题而不是 bug。升级兼容也全无：没有迁移框架、没有迁移前备份，加一列就 ALTER 一列，downgrade 直接坏。
- **whyBlind**：因为单机单实例下永远测不出来——所有测试都是单进程起 server。『并发』在 dev 心智里不存在，直到用户真实地『开着桌面端又开个 CLI』。schema 演进用 _ensure_column 无痛加列，掩盖了没有版本号这个事实，直到某次加列遇到冲突字段或需要 downgrade。
- **Modus 触点**：src/modus/desktop/db.py 全部 connect/ALTER · src/modus/entrypoints/cli.py 与 mcp_server.py 的启动路径 · src/modus/policy/verification.py 的独立 sqlite 连接 · src/modus/desktop/session_state.py 的内存态归属
- **风险**：租约机制在无头/服务器场景会挡掉合理并发；WAL 多读单写已缓解读锁，但写者互斥引入新故障面；迁移框架一旦出错会波及用户全部历史，需要强测试。
- **payoff**：多入口产品形态（CLI+Desktop+MCP+后台）第一次是安全地共用一份数据的，升级从『加列碰运气』变成可审计、可回滚的正式动作。这是『产品化』和『能用』之间的那条线。
- **落地步骤**：给 desktop.db 引入 PRAGMA user_version + 迁移表：版本常量、逐个 forward migration、迁移前先做原子备份（copy 到 .bak 再 ALTER），从 _ensure_column 里迁出。；加实例协调：db.py 顶层加『writer 租约』——启动时 acquire 一个 instance 文件（flock/msvcrt），第二个写者进程被拒绝并提示『另一实例在运行』；只读查询（code_index、recall）可并发。；把 CLI/Desktop/MCP 三个入口收敛到同一个启动例程：检查租约 → 跑迁移 → 才允许写；违反时给出明确错误而非默默竞争。；写升级兼容文档 + 测试：旧版 DB 文件 → 新版迁移成功且保留用户历史；反向 downgrade 被显式拒绝而非坏掉。；加双实例并发回归测试：两个进程同时 open/写，断言租约阻止第二个写者，数据无损。


### 用户视角

**总判断**：从终端用户视角看，Modus 在"单次运行内把事情做漂亮"上极其成熟（验证门、预算、重试、审批、记忆、工具），但几乎全部能力都以"用户此刻坐在屏幕前、这台机器、这个进程、连着网"为默认前提。真正的盲区不在工具数量，而在四个用户会天天遇到、架构师从"任务执行"视角根本看不见的时刻：关机后回来（连续性）、给出一半指令后中途反悔（可干预性）、机器比人先感知到问题（主动性）、以及普通人在不可恢复操作上的信任门槛（可回退性）。这四个方向把 Modus 从"一个很听话的执行器"推向"用户愿意长期托付的桌面伙伴"。

#### 世界不能在我关机时消失——跨重启/断电的连续性层（persist-as-a-service）

- **thesis**：普通用户的真实使用节奏是"关盖走人、打开继续"，而不是坐在终端前等一个 run 跑完。Modus 把全部心思放在"单次运行内做得漂亮"（验证门、预算、重试、审计），但对用户而言，一个合上电脑两天后回来、对"上次那件事"一脸茫然的 Agent 是不值得托付的。现在 resume_session 只覆盖 WebSocket 断开后在同一进程内的 park/resume（server.py 约 3684 行），budget 快照会落盘，但没有任何"进程重启或断电后恢复会话状态"的机制——断电/换机后 Modus 既不能主动告诉用户"你有 3 个未完成任务"，也无法重建上次的现场（记忆是 session-scoped，而数据只在本地文件）。用户的连续性是被低估的第一需求。
- **whyBlind**：架构师的开发流是"一次跑完一个任务"，断点恢复只是工程角落；但终端用户的日常是打断式、多天多任务交错。功能地图把"调度器/后台 agent/持久 run 状态"列为缺口，但只从"让任务继续跑"的角度看，没从"让用户找回自己的世界"的角度看。
- **Modus 触点**：resume_session 处理器（desktop/server.py）；RunBudget 落盘快照（runtime/budget.py + process_tools 注册表落盘）；stopping.py 的 ProgressCheckpoint 字段；desktop/session_management 的 session export
- **风险**：自动认领后台进程有真实危险（reaper/atexit 语义要区分"上次崩溃留下的进程"vs"用户自己开的进程"），需要新增审批或按注册表 ownership 判定的规则；launchd 自启牵扯 TCC/FDA 权限面，安全审查成本高
- **payoff**：这是"个人 PC 基座"与"一个 REPL"的分水岭：断电/换机后用户仍能找回自己的世界，Agent 才从工具变成可托付的伙伴；同时解锁调度器（开机跑昨晚没跑完的任务）作为副产品
- **落地步骤**：新增持久化 intent ledger：每次 run 完成/中止时写入一条结构化记录（意图、停止原因、完成度、工作区路径、最后验证状态、artifact 引用），独立于 messages 表，索引按"未完成"优先；实现 desktop 启动时的 recovery sweep：启动后扫描 ledger，把"未完成任务"聚合成"上次的世界"卡片（3 个未完成任务 + 各自的最后状态 + 一键继续），并支持重新挂接后台进程注册表（process_tools 已有落盘 registry，只需在重启后重新认领而非孤儿化）；给 resume 语义加上"restart-safe"：把 resume_session 从单进程 park 提升为"从 SQLite 现场重建 run"（budget snapshot + 已执行计划 + 剩余步骤），复用 stopping.py 的 checkpoint 字段；做一次人工模拟：杀掉进程、改一行工作区文件、重启，验证 recovery 能给出"上次做到 X，我发现工作区已变化，要继续吗"；把 CLI serve/desktop 包上 launchd/Windows 自启 + 崩溃自动拉起，让"Modus 一直都在"成为默认

#### 给出一半指令、中途反悔——中途改道的用户干预路径（park-edit-resume）

- **thesis**：用户不会像开发者那样把需求想清楚再交给 Agent。真实用法是：说到一半就打断——"等等，这个不用做了，先看看 B"，或者看 Agent 正在改文件时发现方向错了。Modus 有 run_message 注入、有 cancel、有 checkpoint，但三者是割裂的：run_message 只是追加文本，cancel 是终止，中间没有一个"暂停当前 run → 让用户看 checkpoint → 改目标 → 原地继续"的动词。对一个全能基座，"中途改道"是比"完整执行"更频繁的调用场景，而架构师从"task 完成率"指标根本看不到它。
- **whyBlind**：开发流里 Agent 是被 prompt 驱动的一次性工具，打断是异常路径；但终端用户的工作方式天然是迭代的、口语的、边走边想。验证门和审批门都是"用户批准 Agent 的下一步"，没有任何一个门是"用户推翻自己的上一个指令"。
- **Modus 触点**：run_message 处理器与 cancel 分支（desktop/server.py 约 3790 行）；snapshot.py 的 revert_turn 与 side-git 快照；runtime/verification.py 的验证失效语义；审批流程 approval_flow
- **风险**："重新验证"语义容易做重：改道后全量重跑会浪费预算，需要按改动影响裁剪；这个功能直接碰 Agent 循环核心，改动面大且难写不变量测试
- **payoff**：把"给 Agent 下指令"从一次性提交变成持续对话，用户试错成本断崖下降；这是普通人敢对 Agent 说"先做起来我看看"的前提——没有它，Agent 只敢被用于想清楚的任务
- **落地步骤**：复用 snapshot.py 已有 revert_turn：在桌面 WS 层暴露"interrupt → snapshot → user review → redirect → resume"消息流，先把 park 语义从"仅 WS 断开"推广到"用户显式中断"；新增"目标 diff"界面：当前目标与用户新指令并排显示，Agent 在被要求改道时先输出"改动影响清单"（哪些已完成验证、哪些会被推翻、哪些文件受影响）再等确认；把 run_message 升级为结构化指令：区分 append-context（现在）vs re-target（改目标，触发 checkpoint 对比）vs escalate（放大范围，触发新 plan 审批）；给修改过的文件打"unverified since redirect"标记：改道后旧的验证结果自动失效，直到新目标下重跑

#### 机器比人先发现问题——主动守护模式（idle-watch + battery-aware）

- **thesis**：用户对"全能 Agent 基座"最深的隐性期待不是"你听我的命令"，而是"你会看护我"。但 Modus 现在是一个被动响应系统：系统只在用户发指令时动作，system_probe 是"Agent 想了解机器"时主动调用的透镜，probe 出的 cpu/disk/进程数据没有任何跨 run 的持续监控语义，也没有电池信息。真实用户场景是：下载到一半、屏幕合上、磁盘要满、后台跑了个编译——他们希望 Agent 在"我离开屏幕"的时候替我看着，而不是等我回来描述症状。这让 Modus 从"工具"进入"伙伴"维度的最短路径，也是架构师最容易当作"玄学/情感价值"而轻视的一类能力。
- **whyBlind**：system_probe 的定位是"读透镜"（安全、默认放行），设计者关心的是"Agent 能读到什么"，而非"系统何时需要被人看"。守护模式是 OBSERVE/SUGGEST 自主级别（蓝图已有概念）但从没被当作一等用例。而且它需要"Agent 主动发起"，而当前 agent.py 的循环本质是 request/response。
- **Modus 触点**：system_probe schema（tools/system_probe.py，需加电池与活动字段）；process_tools 注册表 + reaper（复用为守护采样器）；summarizer + self_report（合成离场摘要）；timeline 事件流（desktop/static/timeline.js）
- **风险**：守护循环若失控就是自旋烧预算（蓝图已明确风险）；"Agent 主动发起"需要新的自主级别与预算语义，且通知能力若不限频会变成骚扰；隐私边界要严格限定在本机、无云上传
- **payoff**：唯一让用户觉得"这台电脑在替我操心"的能力；守护+离场摘要把被动工具变成主动伙伴，并且是完全可安全落地的（全部只读、全部本地、可撤销）
- **落地步骤**：扩展 system_probe schema 加 battery + last-user-activity（上次输入/移动/屏幕亮灭）两个字段，全部只读、零权限面；建 idle-watch daemon：用进程注册表 + probe 周期性采样（如 60s），维护"用户离开期间发生了什么"的 delta 日志（进程崩溃、磁盘增长、网络任务完成），写入事件表；用户回来时在 timeline 顶部推一条"你离开的 40 分钟里"摘要（复用 summarizer + self_report 的模块），优先级高于历史消息；实现"可预期事件"守护：下载完成/编译结束/磁盘超阈值 → 可选 OS 通知（走系统通知，不是 agent 输出），绑定到任务对象（蓝图任务对象：有界、可撤销）；以"电池还剩 15% 且有个长任务在跑"这类真实场景做验收测试

#### 普通人的信任门槛——全局回滚与"出事了能反悔"

- **thesis**：决定普通人是否敢把电脑交给 Agent 的，不是工具多不多，而是"它搞砸了能不能回来"。Modus 的 snapshot.py 已有 side-git revert_turn，但它是工具层原语——没有任何 WS 消息或 UI 把"回滚这次 run 的所有改动"暴露给用户，timeline 与 kanban 前端零 revert 接线。而记忆层的回滚更脆弱：memory 只有 active/archived 状态，没有"记忆变更历史"，Agent 记错一条偏好，用户不知道也不可撤销。对一个面向普通人的基座，"可回退性"是信任的基石：比加任何新工具都更值得做，而架构师在评估"能力完整度"时几乎从不把它算作能力。
- **whyBlind**：开发者把 revert 当作 git 技能的一部分（工具层面有就行）；但普通人把"出了事能不能回到一分钟前"当作是否敢用的唯一标准。能力矩阵只看"能不能做 X"，从不看"做了 X 能不能撤销 X"——撤销原语存在却被视为当然，从没被提升为一等用户可见能力。
- **Modus 触点**：snapshot.py 的 create/restore_snapshot 与 revert_turn；desktop/server.py WS 消息路由；memory.py + db.py 的 memories 表（需加不可变 audit）；desktop/static/timeline.js 与 kanban.js（加回滚入口）
- **风险**：回滚是危险动作（可能丢用户自己在 run 期间的手工改动），需要和审批门耦合且谨慎定义"run 的边界"；记忆 audit 会放大存储与检索复杂度
- **payoff**：直接拉低普通人第一次大胆使用 Agent 的心理门槛；把已存在的 snapshot 从工程设施提升为可见产品能力，零新增底层、几乎纯接线，性价比极高
- **落地步骤**：在桌面 WS 加 run-revert 消息流：基于 snapshot.py 现有 revert_turn，暴露"回滚此 run 全部改动"，返回影响清单（N 文件还原、M 文件新增保留），UI 放一个显眼的回滚按钮；给 memory 层加"记忆变更历史"：每写一条记忆就追加不可变 audit 行（who/时戳/原文），用户可在记忆面板一键"撤销这条记忆"或"让我看到 Agent 是怎么记住这句话的"——堵住记忆污染源头，也符合蓝图第 8 条；把 revert 也接到审批/验证门：回滚操作本身走审批，回滚后触发重新验证，避免"回滚到坏状态"；验收场景：Agent 改坏一个文档 → 用户一键回到 run 前 → 确认文件 diff 干净；Agent 记错偏好 → 用户在记忆面板撤销并溯源


### 可靠性视角

**总判断**：整体判断：Modus 的可靠性设计是"单次 run 正确性 + 人工在场"导向——瞬态重试（retry.py）、run 预算（budget.py）、进程清理（process_cleanup.py）、启动 run 对账（interrupt_nonterminal_runs）都做得扎实，time.monotonic 也用得对（时间同步不构成盲区）。但"长期常驻、无人值守"链路是空的：没有运行中的健康回路（system_probe 能读却无任何动作执行器，/api/health 是纯 pull，RunApprovalBroker 审批 future 无超时，浏览器共享 page 无崩溃恢复）；数据平面无任何治理（audit.jsonl 无限 append、WAL 只开不 checkpoint、run_events/artifacts/snapshot 无保留无配额无损坏恢复）；模型是单 provider 单点（非瞬态退化一律 SURFACE_TYPED 终态，无 failover 无离线恢复）；诊断只做运行期即时反应、无失败回放沉淀。四个方向按"进程级健康/数据边界/外部依赖降级/经验自诊断"四个时间尺度覆盖无人值守全链路，每项都落在现有模块的扩展点上而非空谈。

#### 驻留健康回路 + 自愈动作执行器（watchdog daemon + 自动降级/修复）

- **thesis**：Modus 的一切诊断都是 pull 式/人工式：system_probe 能读磁盘/CPU/内存/进程，但没有任何代码根据读数采取动作；/api/health 只在被请求时才返回；审批 future（RunApprovalBroker）无超时，无人值守时 run 可永久卡在 ASK 闸门上。无人值守基座需要的不是'更准的探针'，而是'常驻、低权限、fail-safe 的健康回路 + 有限动作集合'——这正是 daemon/守护进程与普通交互循环的分水岭。
- **whyBlind**：所有可靠性机制都挂在 run/会话生命周期内（budget 在 begin_turn 检查、reaper 在 run 结束清理），天然'看不见'进程级与跨会话级失效。系统健康与 run 健康是两个时间尺度，现状只覆盖了后者。
- **Modus 触点**：tools/system_probe.py（复用探针）、tools/browser.py（_ensure_browser/_holder 生命周期）、desktop/approvals.py（RunApprovalBroker 超时）、desktop/server.py（启动注入）、desktop/db.py（WAL checkpoint）、policy/audit_log.py（动作留痕）
- **风险**：watchdog 本身会成为新的失效点：动作必须 fail-safe（探针失败=不动作）、低权限（只清理 Modus 自己的数据目录，绝不删用户文件）、且不能与 run 生命周期抢锁。自动重启浏览器可能打断进行中的交互，需要阈值与通知。
- **payoff**：这是'无人值守'从口号变成能力的核心：无需用户在场，基座能自愈磁盘占满、审批挂死、浏览器崩溃三类最常见故障，并让用户回来时看到'发生了 X、我做了 Y'的审计轨迹。
- **落地步骤**：新增 modus/health.py：常驻 watchdog 任务，周期（60s）采样磁盘余量（shutil.disk_usage on ~/.modus）、audit.jsonl 大小、SQLite 大小、approvals 待决时长、浏览器 page.is_closed()。复用 system_probe 的探针函数，不重复造轮子；在 desktop/server.py 启动时 spawn watchdog 任务（与 install_process_cleanup 平行），动作表做成显式枚举：PRUNE_CACHE（清理 WAL 与过期 artifacts）、RECYCLE_BROWSER（自动 _close_browser 重开）、DENY_STALE_APPROVALS（对超时审批 future 置 deny，并在 engine 层解卡）、NOTIFY_USER（WebSocket/桌面横幅）——每个动作都要审计日志；给 RunApprovalBroker 加 timeout（如 10min，run budget 内可配置），approval_callback 等待超时自动置 deny 并继续 run 而非挂死；在 default_runner 的 approval_callback 里包一层 asyncio.wait_for；watchdog 检测到磁盘剩余低于阈值时自动触发一次 WAL checkpoint + VACUUM，并按保留期清理旧 run_events/artifacts；这个修剪动作同时复用方向 2 的数据治理组件；为 browser.py 加 page 健康检查：watchdog 或工具调用发现 page.is_closed()/渲染进程崩溃时自动 relaunch（把 _holder 重置再 _ensure_browser），无需用户手动 browser_close

#### 数据平面治理：审计/事件/快照的保留、配额与损坏防护（storage 安全边界）

- **thesis**：audit.jsonl 是无限 append-only 且无轮转；run_events/memories/artifacts 无任何保留或删除策略；WAL 只开不 checkpoint；snapshot 侧 git 库按 turn 累积提交永不 gc。一个常驻基座只需数月就会让 ~/.modus 无限膨胀——而且所有写入都未做损坏检测。可靠性视角的盲区不是'没空间'，而是'数据平面无边界、无配额、无腐败恢复'。
- **whyBlind**：数据治理看起来像运维杂活，不在 run 正确性主线上；且磁盘占满往往是慢变量，单次开发会话观察不到。但它是无人值守故障的根因之一（磁盘满→SQLite 写失败→run 全挂）。
- **Modus 触点**：config.py（新增 StorageConfig）、policy/audit_log.py（轮转+降级）、desktop/db.py（prune/WAL/VACUUM/quick_check）、tools/snapshot.py（保留策略）、desktop/memory.py（memories 过期）
- **风险**：修剪必须保守且可逆：删除策略默认关闭、只删 Modus 自己的数据、绝不触碰用户文件；损坏恢复路径本身需要测试覆盖。审计日志轮转会改变审计连续性，需在轮转时记录索引。
- **payoff**：让基座可无限常驻而数据面有界：磁盘占满这一无人值守头号杀手的根因被治理，且所有数据获得腐败自愈——这是'长期存在'最硬的要求之一。
- **落地步骤**：在 config.py 加 StorageConfig：audit 轮转阈值（如 100MB 切分并只保留 N 份）、run_events 保留天数、memories 软过期、artifacts 上限（字节/数量）；新增 db.prune_expired() 与 audit_log.rotate() 两个幂等函数；为 audit_log.py 的 record 增加 write 失败降级：磁盘满时不再 raise（现在是 open 直写可抛 OSError），降级为内存最近 N 条并在健康回路上报——审计是安全不变量，不能因磁盘满而静默丢失；SQLite 打开时（_get_conn）加 PRAGMA quick_check 周期/启动校验 + 损坏时的 recovery 路径：备份坏库到 .modus/backup/ 后重开新库并从 run_events 重放重建 run 台账（与 interrupt_nonterminal_runs 的修复语义一致）；给 snapshot 侧 git 库（tools/snapshot.py 的 data_path('snapshots')）加 gc/保留策略：按 run 只保留最近 N 份快照，超限删除对应 side-repo 分支；启动时对 ~/.modus 做一次性配额报告：把 db 大小、audit 大小、artifacts 大小、snapshot 大小写进健康面板，供用户与 watchdog 共读

#### 模型/网络优雅降级：provider 故障转移、静默模式与断线可用性

- **thesis**：retry.py+errors.py 把 429/5xx/timeout/context_overflow 分类得很细，但 recovery_policy 对 auth/billing/model_not_found 一律 SURFACE_TYPED 终态，且 create_llm_client 是单 provider 单点——没有备选模型路由。对无人值守基座，模型不是'要么成功要么失败'，而是'降级后继续干活'：DeepSeek 挂了应路由到备用 provider 完成已开始的工作，而不是整个 run 死亡。
- **whyBlind**：瞬态重试已有，但'持续性退化'（配额耗尽、模型下线、API key 过期、供应商长时间 5xx）没有任何策略——它被当成了终态而非可管理的运行状态。且 config 只有单套 llm 配置，无 failover 拓扑。
- **Modus 触点**：llm/retry.py+errors.py（failover 触发与事件）、llm/factory.py（RouterClient）、config.py（fallback 链）、agent/strategies/react.py（force_compact 分支）、mcp_client.py（重连）、desktop/session_state.py（recoverable run 复用）
- **风险**：多 provider 路由引入新失效面：fallback 到不可信 provider 的密钥管理、降级导致行为漂移、切换判断错误造成 flapping。必须先定义'降级是可审计事件'且默认 fail-closed（不降级）。
- **payoff**：模型/API 是无人值守基座最脆的外部依赖，故障转移+离线恢复让单点依赖变成可用性资源——这是从'开发工具'到'常年可用助手'的分水岭。
- **落地步骤**：在 LlmConfig 增加 fallback 链字段（providers: list[dict]，含 provider/model/api_key/base_url），factory.create_llm_client 返回 RouterClient：主 provider 在 retry 用尽后按 RecoveryAction 是否允许降级来决定是否切到下一环，切换后向上游 emit 一条 typed 的 failover 事件；在 retry.py 的 retry loop 中把'连续 N 次超时/429'升级为 failover 触发（区别于偶发重试），并把 FORCE_COMPACT 降级路径（context_overflow 时压缩后换模型）接到 react.py 已有的 force_compact 分支；新增 offline/degraded 模式：网络全断时 run 不硬失败，而是把未完成意图+现场（budget snapshot、上下文、失败原因）落盘为 recoverable run（state='interrupted'/'degraded'，stop_reason='network_unavailable'），恢复后用户可一键 resume——复用已有的 park/resume 与 interrupt_nonterminal_runs 语义；为 MCP 客户端（mcp_client.py）加自动重连：stdio 进程退出/SSE 断流时按退避重连并 refresh_tools，MCP 工具不可用时不把 run 判死，而是把该工具标记为 temporary_unavailable 让模型换路径；在 hitl_mode=auto 下引入'静默优先'策略：网络退化或模型退化时自动下调并发（max_concurrent_read）、加大压缩触发、并优先走本地确定性工具（snapshot/code_index/system_probe）完成可离线部分

#### 自主运行的任务证明/自我诊断：run 级 watchdog 与故障根因回放（self-diagnosis loop）

- **thesis**：budget.turn_records 已经记录了 turn 级观测（text/thinking/tool_calls/errors/stall），verification gate 也能判定结果真伪——但这一切只在 run 运行时被消费，run 失败后没有任何'为什么失败'的沉淀。无人值守场景下没人盯着终端，故障根因必须从审计数据自动回放生成诊断：这是把 turn_records/audit/run_events 变成可查询的失效回放，而非只服务于单次运行的在线监控。
- **whyBlind**：现有自省（stall 检测、tool_error_hotspot、NO_PROGRESS）都是运行期即时反应，面向'正在跑时把 run 停下来'；没有人问'跑完之后，把失败 run 的因果链重放出来给下一次 run/用户看'——回放视角缺位。
- **Modus 触点**：runtime/budget.py（turn_records 已是数据源）、desktop/db.py（run_events/run 台账）、agent/self_report.py（报告结构复用）、agent/strategies/select.py+plan_execute.py（启动预置）、runtime/verification.py（验证 gate 持久化）、tools/executor.py（降权影响面）
- **风险**：诊断回放本身可能误判根因（相关性≠因果），预置 hint 若错误会污染新 run——必须保证所有建议是低优先级参考（reference-only，与 episodic recall 同语义）且可一键关闭。
- **payoff**：让基座从'会自停'进化到'会自诊断'：无人值守时故障不是黑盒丢失，而是自动生成'发生了什么、为什么、下次怎么避免'——这正是长期自主运行最稀缺的能力。
- **落地步骤**：新增 post-run 诊断：run 结束时把 budget.turn_records + usage_ledger + 失败 event 序列 + approval 决策沉淀为 run_meta 摘要（复用 desktop/db.py 的 run 台账与 run_events），形成'失效签名'；新增 diagnosis 工具/面板：给定 run_id，重放 run_events 生成因果链（N 次工具失败→验证不通过→回退→terminate），并输出可执行的修复建议（如'tool X 重复失败，考虑禁用/换策略'），复用 self_report.py 的自我报告结构；把自诊断接到 select.py 与 plan_execute.py：新 run 开始时自动检索同 workspace 的失败签名，若当前请求命中已知失败模式则预置 hint/预设策略，形成'经验驱动的启动配置'；给 budget.stalled_for 与 verification gate 的触发加持久化计数：连续 N 次 NO_PROGRESS/VERIFICATION_REQUIRED 的 run 自动进入'升级'路径——降低权限期望、换 agent_mode、或转人工队列（与 hitl_mode 联动）；健康回路（方向1的 watchdog）读取近 N 个 run 的失败签名做退化检测：同一工具连续失败率上升时自动降权（影响 executor 的读并发与重试预算）
